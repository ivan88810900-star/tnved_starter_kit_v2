# DM-0011 — Структурированная применимость NTM и curated shadow enforcement

> **Status:** Accepted — implementation boundary; production activation deferred
> **Decision:** Ivan, 2026-08-15
> **Depends on:** DM-0008, DM-0009, DM-0010

## Context

Полный официальный NTM-контур из DM-0008 обеспечивает видимость девяти семейств,
но совпадение по префиксу, свободному тексту или строке «из» намеренно остаётся
`needs_clarification`. Для более точного ответа нужны структурированные факты
сделки и товара: направление, страны, назначение, состав/CAS, технические
параметры, упаковка, вид переработки, реестровые сведения и исключения.

Отдельная проблема — не смешать точный advisory-вывод с broker/missing-check.
Пользователь поручил выполнить все пункты плана, включая exact applicability и
подготовку curated enforcement. Это разрешает реализацию и shadow-проверку, но не
отменяет прямую границу DM-0008: production enforcement требует отдельного
явного rollout-решения.

## Decision

Принята следующая граница реализации.

1. API принимает необязательный объект `facts` с закрытой Pydantic-схемой.
   Неуказанный факт считается неизвестным; неизвестность не превращается в
   отрицательный юридический вывод.
2. Broad-контур остаётся safety net для всего каталога. Bounded exact evaluators
   покрывают только source-backed allowlist:
   - Решения КТС №299, №317, №318 и Решение Совета ЕЭК №157;
   - разделы 2.16/2.19 Решения Коллегии ЕЭК №30;
   - ограниченные строки 1.2/2.2/2.3/2.30 Решения №30;
   - шесть списков экспортного контроля РФ как HS-candidate index и отдельные
     exact правила, а также transaction-level проверку статьи 20 №183-ФЗ.
3. Exact-результат может иметь `definite` или `excluded` только при совпадении
   точного кода, условия наименования и всех обязательных structured facts.
   Он остаётся advisory: `used_for_missing_check=false`, manual review обязателен,
   live registry lookup этим модулем не выполняется.
4. Curated enforcement bridge реализуется как отдельный versioned allowlist с
   переменной `NTM_V2_OFFICIAL_CURATED_ENFORCEMENT_ENABLED`. Значение по умолчанию
   — **OFF**. При OFF bridge формирует только audit и не изменяет broker. Даже при
   ошибочном включении флага caller-supplied facts не проходят trust gate:
   требуется отдельная метка доверенного adapter-а и `trusted_source_verified=true`.
5. Первая frozen-версия allowlist содержит только две exact shadow-строки:
   `D30-2.30-HCB-2903920000` и `RF-PP1284-2.1.1-AMITON`. Prefix, marker,
   candidate-only, неполные и отрицательные строки технически не могут попасть в
   broker.

## Trust and rollout boundary

Structured facts в текущем API являются данными вызывающей стороны. Поля о
реестровой проверке не означают, что сервис сам сходил в официальный реестр.
Runtime exact-строки поэтому имеют `evidence_trust=caller_supplied_structured_facts`
и технически не могут попасть в broker. Сам feature flag без trusted provenance
не активирует ни одного документа.
Поэтому production flag остаётся OFF до выполнения всех условий:

- отдельное явное решение Ivan о включении конкретной версии allowlist;
- доверенный adapter для официальных реестров/документов с provenance;
- юридическая повторная проверка exact rule и отрицательных golden-тестов;
- shadow-метрики на реальном трафике без влияния на статус;
- runbook rollback и подтверждённая возможность мгновенно поставить flag в OFF.

Включение флага без этих условий не разрешено настоящим решением.

## API and UI contract

- `facts` additive и backward compatible; запросы без него сохраняют прежний
  broad-only ответ.
- UI показывает missing facts, точную строку, редакцию источника и ограниченное
  исключение. Exact advisory визуально отделён от обязательных и отсутствующих
  документов.
- Всеобъемлющий экспортный контроль является проверкой сделки, а не
  автоматическим документом по коду ТН ВЭД.
- При `export`/`transit` legacy import broker и импортный расчёт платежей не
  применяются. Локальные санкционные HS/страновые данные также не выдаются за
  экспортный screening: проверяется только указанный контрагент, остальное
  маркируется для ручной проверки.
- Транзит не считается автоматическим отрицанием меры: ветеринарные и
  фитосанитарные строки остаются `needs_clarification`, а криптографический
  контур различает только три явно заданных маршрута из приложения №9.
  Исключение приложения №5 требует отдельного факта `natural_person=true`;
  одного пользовательского признака «личное использование» недостаточно.
- `not_detected` не означает юридическое отсутствие меры.

## Rollback

1. Установить `NTM_V2_OFFICIAL_CURATED_ENFORCEMENT_ENABLED=0` — broker возвращается
   к прежней семантике без миграции БД.
2. При проблеме advisory установить
   `NTM_V2_OFFICIAL_FULL_ADVISORY_ENABLED=false` согласно DM-0008.
3. Exact evaluators не пишут в БД, поэтому data rollback не требуется.

## Rejected alternatives

- Enforcement всех broad/prefix совпадений — небезопасен и запрещён DM-0008.
- Молчаливое признание пользовательского `registry_verified=true` доверенной
  проверкой — запрещено без source adapter.
- Глобальное отрицание семейства по одному exact исключению — запрещено; каждое
  исключение ограничено конкретным правилом.
