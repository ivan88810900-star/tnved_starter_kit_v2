# Decision Memo: единый семантический поиск ТН ВЭД

## Context

Основной пользовательский поиск уже прошёл full-data acceptance на 17 809 строках
`tnved_commodities` и использует `hybrid_fts` с детерминированным fallback. Старый
экспериментальный векторный контур хранит JSON-векторы для другой таблицы —
`tnved_entries` — и выполняет запросы только через OpenAI. Автоматическая загрузка
векторов текущим фокусом не разрешена. Нельзя незаметно сделать старый справочник
источником результатов основного поиска или начать расходовать API-квоту на каждый
ввод пользователя.

## Decision required

Какой индекс и провайдер использовать для продуктового semantic rerank поверх
`tnved_commodities`, сохранив `hybrid_fts` источником безопасного fallback?

## Option A

### Description

Новая версионированная таблица эмбеддингов для `tnved_commodities`; серверный OpenAI
для пакетной индексации и явного AI-поиска.

### Pros

- минимальная переделка существующего HTTP-клиента эмбеддингов;
- сильная мультиязычная модель;
- понятная размерность и версия модели.

### Cons

- внешняя стоимость индексации и каждого нового запроса;
- данные запроса уходят внешнему провайдеру;
- нужен управляемый бюджет, rate limit и кэш.

## Option B

### Description

Та же отдельная таблица по `tnved_commodities`, но provider abstraction с Gemini как
основным провайдером и OpenAI как явной альтернативой (без автоматического fallback
между платными провайдерами).

### Pros

- переиспользует уже существующую серверную интеграцию Gemini;
- позволяет выбрать провайдера конфигурацией;
- исключает привязку продуктового API к одному поставщику.

### Cons

- всё ещё внешняя стоимость и передача текста;
- миграция модели требует полного переиндексирования;
- больше контрактных тестов и операционной диагностики.

## Option C

### Description

Локальная мультиязычная embedding-модель в отдельном worker-процессе, с тем же
версионированным индексом `tnved_commodities`.

### Pros

- нет оплаты за запрос и передачи товарных описаний наружу;
- предсказуемая работа после локальной установки модели;
- подходит для большого количества интерактивных запросов.

### Cons

- заметный размер модели и новые ML-зависимости;
- требования к RAM/CPU и отдельная процедура поставки;
- качество русской таможенной терминологии нужно измерить на golden-наборе.

## Codex recommendation

Принять **Option C как целевую**, но строить provider-neutral storage/API, чтобы
Option B можно было подключить серверной настройкой. Индексировать только
`tnved_commodities`, ключ строки — commodity ID + нормализованный code + model ID +
content hash + catalog revision. AI-поиск запускать явным действием пользователя,
не на каждый символ. Точный кодовый/лексический hit нельзя понижать; semantic слой
только расширяет и переупорядочивает нестрогие кандидаты. При любой ошибке ответом
остаётся принятый `hybrid_fts`.

До утверждения: старый контур остаётся default OFF; автоматической индексации нет;
добавлены только безопасные флаги, диагностика, bounded-memory ranking и optional
LLM readiness check.

## What requires strategic review

- допустимый размер локальной модели и минимальные CPU/RAM;
- можно ли отправлять обезличенный текст товарного запроса внешнему провайдеру;
- бюджет внешнего fallback и политика кэширования;
- golden-набор русских запросов и минимальное улучшение nDCG/Recall относительно FTS.

## Proposed next task if the recommendation is accepted

Добавить Alembic-таблицу versioned commodity embeddings, provider interface, offline
batch builder с dry-run/оценкой размера, golden-набор из реальных обезличенных
формулировок и явный `semantic=true` rerank для `/api/v1/tnved/search`. Флаг default
OFF; никаких фоновых загрузок; frontend показывает AI-режим и причину fallback.
